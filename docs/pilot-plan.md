# Shared loader pilot rollout plan

This pilot validates a shared preparation/activation strategy with two deliberately different applications:

1. a Rust HTML-first application with a small optional browser island; and
2. a Flutter web application built with the supported Wasm web path.

The goal is to measure whether shared coordination improves activation latency without weakening the HTML baseline, spending unacceptable data, or creating framework-specific startup regressions. It is not a claim that the two applications share a live runtime or that one manifest can describe unrelated framework outputs.

## Hypotheses and non-goals

### Hypotheses

- An HTML-first page can remain useful while a release is prepared in the background.
- A 150 ms dwell threshold removes most accidental pointer passes while focus/touch intent remains accessible.
- A bounded 50 ms activation handoff captures already-finished preparation without making clicks wait for speculative network work.
- A shared coordinator reduces duplicate downloads and gives both apps comparable telemetry, even though their adapters and activation paths differ.
- Immutable URLs, exact manifests and cache-aware delivery are more important than a framework-neutral “loader” abstraction.

### Non-goals

- transferring a compiled module, Flutter engine or live runtime across a full navigation;
- using Flutter Web WasmGC output in the native Rust Wasmi host;
- automatically booting Flutter or executing generated JavaScript during preparation;
- making MASH/HTMX HTML a WASM runtime;
- promising a fixed percentage speedup before measuring production-like traffic; or
- adding a universal WASI, filesystem, network or process capability to native execution.

## Pilot applications

### Pilot A — Rust HTML-first route

Build a small production-shaped Rust service that serves:

- a server-rendered landing/feature route that is useful with JavaScript disabled;
- a call to action leading to an interactive route or island;
- a real `wasm-bindgen` or Leptos browser artifact generated by the project’s actual build; and
- a release manifest generated from those files, with the glue module and WASM asset identified separately.

The page registers the manifest in a browser coordinator. Hover/focus/idle preparation may fetch only the marked WASM/module assets. The click or route transition always calls the bindgen/Leptos adapter. If enhancement fails, the server-rendered route, ordinary link or form remains usable. The Rust native package may be used in a separate server-side computation test, but it is not the browser adapter for this pilot.

### Pilot B — Flutter web route

Build a small Flutter web application with `flutter build web --wasm` and a custom bootstrap containing the generated `flutter_js` and `flutter_build_config` placeholders. Configure renderer assets locally for the test environment. Keep a static HTML shell outside the Flutter engine, and activate the trusted Flutter adapter only after the user action or route transition.

The pilot should exercise one engine with two views if the product needs multiple surfaces. The coordinator may prepare selected immutable build files, but it must not run the bootstrap, construct an engine or mount a view. `mountFlutterView` owns idempotent view removal. A separate Dart/native cache test may warm verified bytes in a private file store; it must not be counted as warming a WebView or browser cache.

## Rollout stages

| Stage | Scope | Exposure | Exit decision |
|---|---|---:|---|
| 0. Contract and harness | Test-org build artifacts, manifests, fake transport, real browser fixtures, schema corpus | 0% user traffic | All security/lifecycle tests pass; telemetry has stable event IDs |
| 1. Rust canary | One Rust HTML-first route, same-origin assets, static fallback | Internal users, then 10% | No baseline regression; preparation waste and demand success are acceptable |
| 2. Flutter canary | One Flutter web route and one engine/view configuration | Internal users, then 10% | Bootstrap/renderer startup and fallback are reliable on supported browsers |
| 3. Controlled comparison | Rust and Flutter cohorts with cold, warm, retained and disabled-preparation arms | 25% → 50% | Both apps meet guardrails and show an attributable benefit or neutral cost |
| 4. Template adoption | Shared integration template, app-specific adapters and release checklist | Per application | Each new app proves its own manifest, adapter, fallback and measurements |

Use the `ores-wasm-loaders-test` organization for independent consumer checks and end-user-style test traffic where appropriate. Keep main-organization production assets, test-organization assets and experimental branches on separate origins and release IDs.

## Test matrix before exposure

### Contract and security

- Valid v1 manifests parse identically in TypeScript, Rust and Dart.
- Unknown top-level or asset fields, duplicate IDs/URLs, invalid entrypoints and invalid digests fail before network access.
- Uppercase/noncanonical origins, origin paths, user information, query strings and fragments are rejected.
- A redirect is rejected; a 404/HTML error page with an executable-looking URL is rejected by HTTP status or MIME before it is accepted as a module/WASM asset.
- A body with the wrong byte length or SHA-256 is evicted and does not poison demand activation.
- Public preparation sends no credentials and does not follow redirects.
- CSP, CORS, COOP/COEP and worker rules are tested with the exact deployed headers, not only a local permissive server.
- Generated glue and Flutter bootstrap imports are pinned to the release and reviewed separately from coordinator-fetched bytes.

### Lifecycle and race cases

- A pointer pass shorter than 150 ms does not start explicit preparation.
- A 150 ms pointer dwell begins one preparation job; moving away for less than 150 ms of grace keeps it alive.
- Focus retains the lease after pointer exit; blur releases it after the grace window.
- Touch/pointer-down starts the intended target without requiring hover.
- Two components acquire the same preparation lease; releasing one does not cancel the other.
- All leases release before completion; the unclaimed transport observes cancellation and a later activation retries normally.
- Clicking while preparation is pending never waits for the full preparation timeout; it joins for at most 50 ms and then demand-loads.
- Preparation failure, cancellation, policy decline and cache eviction all leave activation able to retry.
- Two concurrent activations with the same adapter share one startup; a different adapter is rejected.
- An adapter that times out or partially mutates the document is not silently replayed by the same owner.
- Deactivation is idempotent at the host level, invokes adapter cleanup when supplied and permits a deliberate new owner.
- `visibilitychange`, `pagehide`, route replacement and app suspension cancel unclaimed work.

### Network and device scenarios

- Cold cache, warm same-document cache, warm after a new document, and expired/evicted cache are measured separately.
- Fast Wi-Fi, high-latency 4G, 2G/slow-2G, offline, intermittent failure and delayed first byte are covered.
- `navigator.connection.saveData` or equivalent product data-saving policy declines optional preparation and leaves the route functional.
- Low-memory/low-CPU devices measure engine startup and memory high-water marks; no claim is made from desktop-only tests.
- Cross-origin marketing-to-app navigation is tested as a separate case; no cache transfer is assumed.
- Browser back/forward cache, reload, tab backgrounding and multiple tabs are tested for duplicate activation and stale release IDs.

### Rust-specific scenarios

- Server-rendered HTML is visible before the island asset arrives.
- The island can be activated from a click with preparation disabled.
- A real generated bindgen/Leptos glue module is used; no handwritten bootstrap or direct `__wbindgen_start` call is substituted.
- An island failure leaves the HTML route and navigation usable.
- If the native package is exercised, raw-WASM execution is bounded by fuel/memory and receives only explicitly configured imports.

### Flutter-specific scenarios

- The custom bootstrap does not auto-start during preparation.
- Activation uses the supported Flutter loader lifecycle and returns a usable view.
- Two views from the same engine can mount/unmount without double removal.
- Missing renderer files, wrong MIME, CSP failure and a failed bootstrap show the static shell/error affordance.
- A browser reload or full navigation creates the correct new document owner instead of assuming an old engine survives.
- The same build is tested on the browser versions and renderer modes the product supports; WasmGC availability is a measured compatibility input.

## Metrics and instrumentation

Attach a stable `attemptId` to every preparation and activation attempt. Record:

- app, release, build commit, page kind, route, browser/device class and cohort;
- trigger (`idle`, `hover`, `focus`, `touch`, `click`, `route`), policy decision and data-saving state;
- selected asset IDs, declared bytes, network-requested bytes, verified/reused bytes, cache namespace and outcome;
- pointer/focus timestamps, preparation start/finish/cancel, click/route time, activation start/finish, first useful view and fallback time;
- activation join duration, whether a demand retry occurred, error code, adapter/runtime and owner ID; and
- memory high-water mark, long tasks/CPU time where available, and server/CDN status/cache data.

Do not infer a cache hit from `transferSize === 0` alone. Browser timing can omit or coarsen fields, and zero transfer can have more than one explanation. Correlate coordinator events with response headers and server/CDN logs. Never include tokens, cookies, private URLs or decrypted configuration in telemetry.

### Primary measures

| Metric | Definition | Review question |
|---|---|---|
| Activation success | Successful usable activation / activation attempts | Did reliability stay at least at the no-preparation baseline? |
| Time to useful view | Click/route intent to an actually interactive surface | Did preparation reduce p50/p75/p95 latency? |
| Warm reuse | Activations whose required verified bytes were already in the intended store / activations | Is the work reusable in the same owner, not merely requested? |
| Demand retry rate | Activations that had to fetch because preparation was incomplete | Is the bounded handoff behaving as designed? |
| Preparation waste | Prepared bytes for releases not activated during the configured observation window | Is speculation costing more data than it saves? |
| Cancellation rate | Jobs cancelled by pointer exit, page lifecycle, policy or activation handoff | Are signals and cleanup working? |
| Duplicate request rate | Same asset/release requested concurrently outside the coordinator’s shared job | Are components using one coordinator? |
| Fallback rate | HTML/static/error fallback shown after a real activation failure | Can users still complete the route? |
| Memory/CPU cost | Engine/module memory high-water and startup CPU/long tasks | Is the speedup worth device cost? |

### Proposed initial guardrails

These are pilot gates to validate, not promises about production performance:

- zero explicit preparation on a sub-threshold pointer pass and zero optional preparation when data saving is enabled;
- no activation path waits longer than the configured 50 ms speculative join before it begins demand activation;
- activation success and fallback completion are no worse than the disabled-preparation control beyond a pre-agreed 1 percentage-point tolerance;
- p95 time to useful view does not regress by more than 5% in the enabled cohort;
- duplicate requests remain below 1% of asset attempts;
- preparation waste is below 30% during the learning stage, with a target below 15% before broad rollout; and
- no unresolved high-severity CSP, origin, integrity, bootstrap or accessibility failure.

If a product cannot meet these values, adjust the trigger/budget/cohort or keep preparation disabled for that route. Do not remove integrity, origin, cancellation or fallback checks to improve a graph.

## Experiment arms and analysis

For each app, compare at minimum:

1. control: no explicit preparation, normal activation;
2. hints only: browser hints but no coordinator preparation;
3. coordinator: idle + intent preparation with the default budgets; and
4. retained shell: coordinator plus an intentionally persistent same-document owner, where the app supports it.

Stratify by cold/warm cache, page kind, trigger, network class, data-saving state, browser, device class and same-origin versus cross-origin navigation. Analyze users who actually click separately from visitors who only saw the marketing page. A decrease in activation latency accompanied by a large increase in never-used bytes is not a successful rollout.

## Release checklist and rollback

Before each cohort increase:

- publish the exact build and generated manifest under an immutable release ID;
- verify content types, CORS, cache headers, CSP and asset-origin allowlists;
- run the shared JSON corpus, host tests, real browser fixtures and app-specific smoke tests;
- confirm the static HTML/error fallback works with preparation disabled and with JavaScript blocked;
- confirm telemetry contains no secrets and has the release/build identifiers needed for rollback; and
- document the feature flag, cohort, rollback release and on-call owner.

Rollback disables optional preparation first; it does not remove the normal activation path. If activation itself is broken, route to the previous immutable application release or the HTML fallback. Keep failed release IDs in telemetry and cache eviction policy so a bad immutable asset is not repeatedly selected.
