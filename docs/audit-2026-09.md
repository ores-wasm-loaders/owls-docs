# OWLS organization audit and hardening record

Audit date: 2026-09-05. Scope: the active repositories in `ores-wasm-loaders`, the external consumer repository in `ores-wasm-loaders-test`, the organization’s legacy repository set, the open implementation/documentation changes, and the shared loader lifecycle used by browser, Dart and native Rust hosts.

## Executive result

The organization has a sound v0.1.1 foundation: a strict release schema, generated language shapes, verified byte stores, explicit adapters and an external consumer/test organization. The main risk was not the idea of a shared loader; it was allowing speculative work to behave like a required startup dependency.

The hardening slice therefore preserves the v0.1.1 wire contract and makes the host behavior additive:

- preparation is represented as a shared, reference-counted job with an explicit outcome;
- activation gets only a bounded handoff to speculative work and then follows its normal demand path;
- intent preparation uses dwell, exit grace, focus retention and page-lifecycle cancellation;
- deactivation can release a retained adapter owner through explicit cleanup;
- browser and native HTTP transports reject missing or mismatched content types before accepting a response;
- origin policy itself is canonicalized instead of relying only on an asset URL comparison; and
- release identity is stable across JSON property ordering and remains bound to detached immutable data.

This is a lifecycle hardening release, not a claim that one universal runtime exists. Browser `wasm-bindgen`/Leptos and Flutter web still require their own generated glue and activation adapters. Native Rust remains raw-WASM/Wasmi only.

## Repository and architecture findings

### Active versus legacy repository set

The organization currently contains the active `owls-*` packages plus older `owl-legacy-*` repositories. The active graph is the coherent product surface:

| Repository | Role | Audit disposition |
|---|---|---|
| `owls-interfaces` | v1 JSON Schema, peer TypeSpec and language shapes | Keep as the contract authority; evolve by schema version |
| `owls-web-loader` | Browser/worker coordinator, adapters, hints and server links | Hardened in this slice |
| `owls-runtime.rs` | Native verified bytes, Wasmi limits and build inspection | Hardened in this slice |
| `owls-flutter` | Dart host, native stores and trusted WebView bridge | Hardened in this slice |
| `owls-docs` | Installation, architecture, rollout and validation record | Expanded in this slice |
| `ores-wasm-loaders-test/owls-e2e` | External consumer and real framework fixtures | Keep independent; add lifecycle cases |
| `owl-legacy-*` | Earlier names/implementations | Freeze as read-only history; do not delete during this audit |

The legacy set should not receive parallel fixes. Once the active packages and test-org consumers are released, add repository-level archival/read-only notices and point users at the active graph. Deletion or archival is a separate owner-approved operation.

### Parallel change review

Two open parallel implementation changes were reviewed before this slice:

- The web-loader merge proposal introduced useful receipts, roles and staged ideas, but its browser path imported a Node `fs`/`path`-based contract module. That cannot ship in a browser ESM bundle. It also did not make explicit-signal preparation share the same job, did not abort work through `cancel`, and let activation wait indefinitely on preparation. Do not merge it as-is.
- The interfaces proposal is a reasonable direction for a future v2 manifest (`role`, `stage`, preparation budget, activation metadata, framework/isolation/toolchain), but it moves runtime policy/validation into the contract package and leaves the TypeScript, Rust and Dart projections behind the schema. Keep those concepts in a versioned design until all peer contracts and host implementations are updated together.

The documentation ideas from those changes are retained here after correcting the lifecycle and browser-boundary problems. A source module used by a browser must be browser-compatible; generated/runtime policy belongs to the host or to a deliberately versioned contract projection.

## Findings and controls

| Finding | Risk | Control in this slice | Remaining owner |
|---|---|---|---|
| Speculative preparation could duplicate or be cancelled by the wrong caller | Extra bytes, races and stale work | Shared preparation leases, claim-on-activation and explicit cancellation | App integration must release leases on teardown |
| Activation could inherit the full preparation timeout | Click latency and apparent hangs | `activationJoinMs` bounded to 50 ms by default and capped by the host timeout | Product can tune the policy after measuring |
| Intent began on accidental pointer entry | Unnecessary data usage | 150 ms dwell, 150 ms exit grace, focus/touch handling and page lifecycle release | Product may choose a larger dwell for dense navigation |
| Failed speculation could be mistaken for failed startup | Broken fallback and unnecessary error UI | `PreparationOutcome`; activation retries through verified demand loading | App must keep HTML/static fallback visible |
| Wrong MIME/HTML error response could reach byte verification | Confusing diagnostics and unsafe integration assumptions | Kind-aware content-type checks in built-in TS, Dart and Rust HTTP transports | Delivery must set correct `Content-Type` |
| Allowlist origin normalization was inconsistent | Host/origin bypass or cache confusion | Canonical HTTPS origin validation and exact asset-origin matching | Product must configure exact origins, not suffixes |
| Retained runtime lacked symmetric cleanup in some hosts | Leaked views/engines and unsafe replay | Optional adapter deactivation in TS and Dart | Framework adapter owns actual teardown |
| Browser PR depended on Node-only code | Browser build failure or accidental server-only path | Browser bundle remains self-contained; no Node contract import | Keep Node-only tools out of runtime entrypoints |
| v2 fields lacked synchronized projections | Cross-language contract drift | Keep current v1 unchanged; require schema/TypeSpec/projection/corpus update as one release | Contract maintainers |

## Code changes

### `owls-web-loader`

- `Coordinator.prepare` now returns a lease whose shared job is reused by callers with or without caller signals.
- `prefetch` resolves a frozen outcome instead of turning a speculative integrity/network/cancellation result into an activation-blocking rejection.
- `activate` claims preparation, joins it only for the policy’s bounded handoff and performs ordinary demand loading after that window.
- `deactivate` invokes an optional adapter cleanup and releases the activation owner.
- `prepareOnIntent` handles keyboard focus, touch, dwell, grace periods, visibility and `pagehide`.
- URL allowlists and release identities are canonical/deterministic, and bindgen adapters validate that generated glue exposes a callable default initializer.
- The built-in transport checks response MIME, streams the declared byte bound and still verifies the exact SHA-256.

### `owls-flutter`

- `WasmHost` now has the same preparation outcome/lease model, bounded activation join and explicit deactivation path.
- `WasmDeactivator<T>` is optional, preserving existing adapters that only implement activation.
- Cancellation carries a reason, protects all cancellation listeners, and distinguishes timeout from ordinary caller cancellation.
- Dart origin parsing rejects noncanonical policy origins and malformed/mismatched asset URLs.
- `HttpAssetTransport` checks kind-aware content types before reading the body, while file cache behavior remains separate from WebView/browser caches.

### `owls-runtime.rs`

- `HttpTransport` checks the response content type for WASM, modules/scripts, fonts and data before bounded streaming.
- Policy origins must themselves be canonical HTTPS origins.
- The native runtime remains constrained to raw-WASM with explicit imports and Wasmi fuel/memory/instance limits.

The v1 schema and `owls-interfaces` projections are intentionally unchanged in this hardening slice. MIME, cancellation, join budgets and adapter cleanup are host lifecycle semantics; adding them as manifest fields requires a new contract version and synchronized projections.

They do not replace the real Chromium framework fixtures, physical iOS/Android/WKWebView coverage, production CDN measurements or app-specific Leptos/Flutter startup tests. The external test organization should consume the published packages independently before the first production cohort.

## Release gates

Before publishing or widening the pilot:

1. Run the shared contract corpus through every projection and host.
2. Build real Rust/Leptos or bindgen and Flutter web artifacts and derive manifests from the exact output.
3. Test same-origin and cross-origin marketing/application navigation separately; never assume cache or compiled-runtime transfer.
4. Verify immutable URLs, CORS, content types, cache headers, CSP, worker policy and renderer asset delivery.
5. Exercise the pilot matrix in [the rollout plan](pilot-plan.md), especially click-during-warmup, data saving, hidden-page cancellation, integrity failure and fallback.
6. Compare enabled preparation with no-preparation and hints-only controls before claiming a benefit.
7. Ship preparation behind a reversible feature flag. Roll back by disabling optional preparation first; preserve ordinary activation and HTML/static fallback.
